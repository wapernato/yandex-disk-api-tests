# Yandex Disk API tests

Проект автотестов REST API Яндекс Диска для заявки на стажировку AQA: **Java 17, JUnit 5, Maven, REST Assured**. Проверяет GET, POST, PUT и DELETE на `https://cloud-api.yandex.net`. Подготовлен по требованиям из задания; проект не является официальным заданием или продуктом Яндекса.

## Быстрый запуск

Нужны JDK **17**, Git и доступ к интернету. Maven устанавливать отдельно не нужно: официальный Maven Wrapper скачивает версию 3.9.11, закреплённую контрольной суммой. Проверенная версия Java — 17; другие версии отдельно не проверялись.

```bash
git clone https://github.com/wapernato/yandex-disk-api-tests.git
cd yandex-disk-api-tests
java -version
./mvnw test
```

В Windows используйте `mvnw.cmd` вместо `./mvnw`. Если Maven уже установлен, можно использовать `mvn`.

| Команда | Что запускает | Нужен настоящий токен |
| --- | --- | --- |
| `./mvnw test` | 37 локальных проверок инфраструктуры | Нет |
| `./mvnw -Pauth verify` | Локальные проверки + 8 запросов к реальному API с отсутствующим/невалидным токеном | Нет |
| `./mvnw -Plive verify` | Локальные проверки + 8 auth-сценариев + 20 сценариев работы с ресурсами | Да, только тестового аккаунта |

`test` сам по себе не проверяет доступность Яндекс Диска. Интеграционные классы `*IT` запускает Maven Failsafe на фазе `verify`. Не ограничивайтесь `integration-test`: ненулевой результат корректно проверяется на `verify`. При отсутствии токена профиль `live` завершается ошибкой настройки, а не скрытым пропуском тестов.

## Отдельная тестовая учётная запись и OAuth

1. Создайте отдельный Яндекс ID для автотестов и откройте его Диск, чтобы активировать сервис. **Личную учётную запись использовать нельзя.**
2. Войдите именно в тестовый аккаунт. По [инструкции Яндекса](https://yandex.ru/dev/disk-api/doc/ru/concepts/quickstart) создайте OAuth-приложение с правами `cloud_api:disk.read` и `cloud_api:disk.write`. Этих прав достаточно для сценариев ресурсов; тесты не запрашивают информацию обо всём аккаунте.
3. Скопируйте ClientID и откройте `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`, заменив `<ClientID>` идентификатором приложения. Разрешите доступ тестовому Диску и сохраните выданный токен приватно. [Полигон](https://yandex.ru/dev/disk/poligon/) также помогает изучить API.
4. Передайте токен через переменную окружения. Пример для Bash/Zsh вводит его скрыто и не сохраняет значение в истории команд:

```bash
printf 'OAuth token for the dedicated test account: '
read -r -s YANDEX_DISK_TOKEN
printf '\n'
export YANDEX_DISK_TOKEN
export YANDEX_DISK_TEST_ACCOUNT=true
./mvnw -Plive verify
unset YANDEX_DISK_TOKEN
```

PowerShell:

```powershell
$secureToken = Read-Host 'OAuth token for the dedicated test account' -AsSecureString
$env:YANDEX_DISK_TOKEN = [System.Net.NetworkCredential]::new('', $secureToken).Password
$env:YANDEX_DISK_TEST_ACCOUNT = 'true'
.\mvnw.cmd -Plive verify
Remove-Item Env:YANDEX_DISK_TOKEN
```

`YANDEX_DISK_TEST_ACCOUNT=true` — явное подтверждение пользователя, а не автоматическое определение типа аккаунта. Проверить, что это отдельный тестовый Яндекс ID, нужно до запуска. `.env.example` содержит только названия переменных; Maven **не загружает** `.env` автоматически. Токен не передаётся через `-D`, не хранится в исходниках и не выводится в HTTP-логах. Не включайте подробное логирование запросов и не публикуйте токен, скриншоты авторизации или локальный `.env`.

## Покрытие

Каждый интеграционный тест работы с ресурсами независим: создаёт собственную корневую папку `disk:/aqa-it-<UUID>`, работает только внутри неё и удаляет её в `@AfterEach`.

| Метод | Позитивные сценарии | Негативные сценарии |
| --- | --- | --- |
| GET | Метаданные папки; пагинация списка детей; кириллица и специальные символы | Несуществующий ресурс — 404; отсутствующий `path` — 400; отсутствующий/невалидный токен — 401 |
| PUT | Создание папки; чтение созданного состояния; имена с пробелами, `+`, `&`, кириллицей | Повторное создание — 409; отсутствующий `path` — 400; имя длиннее 255 символов — 400; авторизация — 401 |
| POST | Копирование пустой папки; асинхронное копирование дерева; перемещение с проверкой старого пути | Отсутствующий источник — 404; конфликт с `overwrite=false` — 409 и сохранение существующего дерева; отсутствующий `from` — 400; авторизация — 401 |
| DELETE | Удаление пустой папки; асинхронное удаление дерева; проверка отсутствия результата | Повторное удаление/несуществующий ресурс — 404; отсутствующий `path` — 400; авторизация — 401 |

Проверяются HTTP-код, JSON-формат, ключевые поля ответа и фактическое состояние ресурса. В ошибках проверяется наличие `error`, `message`, `description`; тексты сообщений не закреплены, поскольку они могут меняться. Основной объект данных — папки и деревья папок. Загрузка/скачивание содержимого файлов, публичные ссылки, квоты, нагрузочное тестирование и PATCH находятся вне текущего покрытия.

## Асинхронность, изоляция и очистка

- Для `202 Accepted` используется возвращённый `href`, проверяются `method=GET` и `templated=false`. Поддерживаются оба документированных вида адреса операции: `/operations?id=...` и `/operations/<id>`.
- `in-progress` опрашивается до `success`. `failed`, неизвестный статус, ошибка HTTP и истечение таймаута завершают тест ошибкой. Повторять POST/PUT/DELETE автоматически нельзя: это могло бы скрыть дефект или создать лишние данные.
- Интервал опроса — 250 мс, таймаут ожидания по умолчанию — 60 с. Его можно изменить через `YANDEX_DISK_OPERATION_TIMEOUT_SECONDS` (1–300). Таймауты подключения/чтения HTTP — 5/10 с; текущий запрос может завершиться позже дедлайна опроса на время своего HTTP-таймаута.
- После завершения операции тест ожидает видимость нового ресурса или 404 удалённого. Другие ошибки HTTP не считаются временной невидимостью.
- Очистка удаляет только созданную тестом папку с UUID и её содержимое с `permanently=true`, без перемещения в общую корзину. Общий корень Диска и вся корзина никогда не очищаются. Защитная проверка пути отказывается удалять произвольные пользовательские пути.
- Ошибка очистки делает тест неуспешным. При аварийном завершении JVM, отзыве токена, недоступности сервиса или незавершённой операции папка может остаться: удалите только соответствующую `aqa-it-<UUID>` на **тестовом** Диске. Ошибка ожидания содержит путь; при ошибке DELETE добавляется диагностический путь очистки.
- Параллельное выполнение отключено для уменьшения нагрузки. UUID позволяют независимым запускам не конфликтовать. Порядок тестов не задан и значения из предыдущих тестов не используются.
- OAuth отправляется в заголовке, редиректы отключены. Ссылки операций проверяются до отправки токена: только HTTPS, точный хост `cloud-api.yandex.net` и endpoint операций.

## Структура и отчёты

```text
src/test/java/io/github/wapernato/disk/
  AuthorizationIT.java          # 8 реальных запросов без валидных credentials
  DiskResourcesIT.java          # 20 тестов ресурсов с отдельным токеном
  support/
    DiskClient.java             # REST Assured, HTTP-настройки, операции API
    TestConfig.java             # окружение, подтверждение тестового аккаунта
    TestNamespace.java          # UUID и защита путей при удалении
    Poller.java                 # ожидание с дедлайном и обработкой interruption
    OperationAwaiter.java       # 202 и статусы операций
    *Test.java                  # локальные проверки инфраструктуры
```

Отчёты JUnit XML и текстовые результаты находятся в `target/surefire-reports` и `target/failsafe-reports`. `target/` исключён из Git. [VERIFICATION.md](VERIFICATION.md) содержит зафиксированный результат выполненных проверок и ограничения.

## GitHub Actions

На push и pull request запускаются только локальные проверки на JDK 17. Вкладка **Actions → Tests → Run workflow** позволяет вручную выбрать `auth` или `live`. Для `live` добавьте repository secret `YANDEX_DISK_TOKEN` с токеном **отдельного** тестового аккаунта и repository variable `YANDEX_DISK_TEST_ACCOUNT=true`. Секрет не нужен для остальных режимов; workflow не получает его на pull request. Отсутствующая конфигурация приводит к ошибке, а не успешному пропуску.
